# H700 — проверки перед планом реализации

**Статус:** пользователь разрешил подготовку отдельной демки и после выявленного link/ABI mismatch согласовал [новое build-окружение ENV-01/02](H700_BUILD_ENVIRONMENT.md). Предыдущая остановка и [результаты демки](H700_GRAPHICS_PROBE.md) сохранены; новый image и повторная сборка проверены: 43 tests, compile/link, ELF/ABI metadata и CPU smoke modes прошли. По отдельному разрешению затем выполнены firmware loader/CPU checks, offscreen (2 кадра) и bridge (120 кадров): программные pixel/order/teardown проверки прошли; пользователь подтвердил видимость квадрантов и маркера при кратком наблюдении. Полная визуальная проверка и возврат меню не подтверждены. Ниже исходный объём исследований; это не утверждённый план переноса и не разрешение менять renderer. Порядок работы — [H700_WORKFLOW.md](H700_WORKFLOW.md), краткий статус — [H700_PROGRESS.md](H700_PROGRESS.md).

## Обязательный фильтр до исследования

Каждый пункт ниже — кандидат на проверку, **не обязательная матрица ради полноты**. До любого исследования/гипотезы/теста пройти [goal gate](H700_WORKFLOW.md): конкретный вопрос пути RG40XX H / muOS 2601 → evidence применимости → минимальная проверка → решение по исходам → условие завершения. Проблема Null или другой вспомогательной среды не становится проблемой Mali автоматически; расширение среды ради её обхода без связи с целевым запуском запрещено. Нужные correctness/security проверки не ослабляются.

## Зачем эти проверки

Вывод изображения через firmware SDL2/Mali уже работает в старом порте. Повторять доказательство этого факта не нужно. Нужно выбрать и обосновать интеграцию с новой базой:

- сохранить новую систему отрисовки и подключить её к проверенному выводу;
- либо адаптировать старую систему отрисовки к новой игре, сохранив необходимые исправления новой базы.

Не разрабатываем оба варианта параллельно. Сначала проверяем конкретные барьеры первого варианта и статически оцениваем объём второго. Стабильные 30 FPS и полное покрытие игровых эффектов не являются критериями этих технических демо: они проверяются на соответствующих последующих этапах.

## PF-01. Контракт графической интеграции — до кода демки

**Вопрос:** поддерживает ли закреплённая версия Dawn безопасное использование firmware EGL display и обмен кадрами с существующим presenter?

**Уже известно:** U использует fork `Odrannnn/dawn`, package `v20261029.114630`, source ref `118436b3f8f68583eb86e811ca605dc41637e8cc`. В соответствующем cached `include/dawn/native/OpenGLBackend.h` действительно объявлены `RequestAdapterOptionsGetGLProc` с `display/getProc` и `WrapExternalEGLImage`. Передача готового EGLContext через эту структуру не объявлена. Наличие API не доказывает доступность функции на конкретном adapter или правила совместного доступа.

**Что получить и выяснить:** исходники этого snapshot, в частности OpenGL/EGL implementation и interop tests. Нужно установить ownership display/context/image, способ создания context, допустимые formats/usage и гарантии GPU completion/синхронизации с внешним GL. Выбрать один поддерживаемый route для демки, не придумывать недокументированный context-sharing API.

Два проверенных адреса вернули HTTP 404:

- `https://raw.githubusercontent.com/Odrannnn/dawn/118436b3f8f68583eb86e811ca605dc41637e8cc/src/dawn/native/opengl/BackendGL.cpp`
- `https://raw.githubusercontent.com/Odrannnn/dawn/118436b3f8f68583eb86e811ca605dc41637e8cc/src/dawn/native/opengl/ContextEGL.cpp`

Это исторический результат этих запросов, не доказательство отсутствия source tree. **Блокировка доступности снята:** пользователь нашёл [Timdeuces/dawn](https://github.com/Timdeuces/dawn), и GitHub API подтвердил в нём точный commit `118436b3f8f68583eb86e811ca605dc41637e8cc`. Реализации прочитаны по этому ref без изменения версии зависимости. Выводы и первичные ссылки — в [H700_DAWN_EGL_RESEARCH.md](H700_DAWN_EGL_RESEARCH.md).

Подтверждены внешний EGLDisplay/proc API, базовый минимум EGL 1.4 и native EGLImage import. Ограниченный single-import/device-lifetime сценарий теперь прошёл на firmware; остаются конкретные вопросы production lifetime, синхронизации и threading. Общая декларация `SharedTextureMemoryEGLImage` не означает её реализации в этом GLES backend. Для минимального опыта рассматривается native `WrapExternalEGLImage`, а не неподдержанный STM route.

**Завершение:** короткое описание поддерживаемого ownership/import/sync route с ссылками на нужный source/API либо конкретный подтверждённый барьер. Этот критерий определён до кода graphics probe; затем выбран и реализован ограниченный single-import/device-lifetime route в [описании демки](H700_GRAPHICS_PROBE.md). Он не закрывает production recreation/cleanup. Ориентир исследования — отдельная сессия до 1–2 часов; если первоисточник недоступен, фиксируем блокировку, не заполняем пробел догадками.

## PF-02. Минимальные build/API проверки — без игры и устройства

**Зачем:** успешная донорская сборка не гарантирует совместимость новых call sites, актуальных зависимостей и ARM64 ABI.

Две небольшие сессии, которые можно готовить независимо от исследования display contract:

1. **SDL fork:** собрать исходники и headers одного донорского pin `6057d79baf8321bf190479a699655f06cc2a962f`; проверить Linux-relevant SDL declarations/exports новой базы, особенно gamepad/HID/PNG/audio, compile/link небольшого API probe. Не инициализировать video/audio на host.
2. **Compiler/MusyX/nod:** проверить C++20 constructs текущего codebase, собрать библиотеку MusyX U и актуальный nod `alpha.12`, выполнить минимальную линковку без чтения диска. Проверить фактические compiler flags и ELF requirements executable/SDL DSO.

**Текущий результат:** SDL и графические APIs собраны/слинкованы в отдельной демке; её ABI gate пройден. Это не полный PF-02: Linux game-facing SDL API audit, MusyX и nod пока не проверены этим harness; переносить этот результат на сборку всей игры нельзя.

**Pass:** компиляция/линковка проходят; нужные API доступны; ARM64 artifacts не требуют более нового runtime, чем firmware. Версии C++ ABI сравниваются с уже полученным firmware evidence. Успешный configure без реальной компиляции недостаточен.

**Fail:** фиксируем точную ошибку и согласуем решение, не откатываем dependencies и не добавляем пустые shims. Если build-only compatibility work требует изменения исходников переноса, это отдельное решение, а не скрытое начало реализации.

Ориентир — по 1–2 часа активной работы на сессию, время cold downloads/build показывается отдельно. Использовать изолированный harness/build directory, исходники приложения не менять. Корневой game configure и полная сборка игры на этом этапе не обязательны. Конкретные команды harness определяются после проверки доступных inputs и согласования исследования.

## PF-03. Одна asset-free демка, два последовательных результата

**До запуска:** завершить PF-01, получить нужные artifacts из PF-02, согласовать сценарий устройства, отдельный test directory, ограничение времени и cleanup. Код демки изолирован от production sources. Игровой образ, настройки и saves не нужны.

### PF-03A. Создаётся ли аппаратное устройство новой графики?

Использовать проверенный SDL2/Mali bootstrap, затем запросить Dawn OpenGLES Compatibility device на firmware EGLDisplay без X11/Wayland surface. Проверить сначала минимальный запрос, затем действительно обязательные limits/features U; учесть существующие texture-fetch/no-compute fallbacks. Выполнить маленький offscreen render и проверку результата.

**Pass:** выбран аппаратный Mali, device создаётся, изображение соответствует ожиданию, нет скрытого software/другого backend и ошибок validation/device loss.

**Результат на устройстве:** offscreen 2 кадра — PASS; Mali-G31, WGSL readback и dedicated-context teardown при минимальном 4096/64 baseline. Последующий `capabilities` создал device с зеркальным default U request и измерил limits/features, но выбранные GX layouts отклонены **17 > 16**. U shader/resource workload не проверен; полный PF-03A не закрыт.

**Fail:** установить, где отказ — package/backend, EGL setup или конкретное требование U. Один неудачный request ещё не доказывает невозможность Dawn. До устранения/объяснения барьера PF-03B не запускать.

### PF-03B. Доходит ли кадр до экрана без нарушения синхронизации?

После PF-03A рисовать простой асимметричный узор и меняющийся маркер кадра, передавать изображение выбранным в PF-01 способом в проверенный firmware presenter. Минимальный discriminator — один постоянный RGBA8 image/wrapper и последовательный доступ с доказанным завершением GPU work; wrapper на каждый кадр не создавать. Проверить pixels, порядок обновлений, orientation/channels и корректное завершение.

Этот bounded single-image сценарий затем реализован по разрешению пользователя в отдельной демке; его device run выполнен по отдельному разрешению: 120 кадров bridge прошли программные проверки; пользователь подтвердил видимость квадрантов и маркера, но пристально за демкой не следил. Два slots, многопоточная топология U и production recreation/cleanup остаются отдельными известными вопросами, которые нужно закрыть до утверждения соответствующей реализации. Успех простого режима не разрешает молча принять упрощённую threading/lifetime policy для игры.

**Pass:** результат совпадает с ожидаемым, нет повреждений, зависаний и повторной записи занятого slot. Передача GPU image работает без CPU readback/upload всего кадра; гарантии ожидания completion определены, а не заменены предположением «submit уже закончил работу».

**Результат на устройстве:** bridge 120 кадров — PASS по diagnostic pixels/order/blit/swap и dedicated-context teardown; видимость квадрантов и маркера подтверждена при кратком наблюдении, не полноценной визуальной проверкой. Проверена одна постоянная RGBA8 texture 64×64, GPU-scaled в drawable 640×480, с последовательным ожиданием и sleep; это не benchmark или production threading test.

**Fail:** локализованный import/sync/context/lifecycle blocker. Readback-upload может помочь диагностике, но не считается подтверждением требуемого bridge. Не менять threading policy новой базы или dependencies в обход согласования.

Подготовку двух режимов разделить на сессии до 1–2 часов, а не обещать полный probe за один короткий запуск. Runtime ограничить заранее; пользовательская визуальная проверка занимает отдельное согласованное окно. Системные библиотеки, частоты, audio route, пользовательские settings и saves не менять. Если безопасный shutdown не определён — запуск не согласовывать.

### Уточнение после device demo: реальный contract U

В [следующем статическом исследовании](H700_DAWN_INTEGRATION_GAPS.md) установлено:

- texture-fetch pipeline layout требует 17/18 fragment textures при эффективном request budget 16/17. Последующий capability test подтвердил на Mali выбор texture fetch без lightmap (vertex storage buffers = 0) и отказ normal/shadow layouts **17 > 16**;
- depth-peek no-compute fallback находится за Core gate: это GX API gap без найденного game-facing потребителя, не доказанная поломка retail-визоров;
- frame packet slots и CPU render-worker barrier не заменяют двусторонний GPU ownership; перенос swap на main требует progress во время блокирующих ожиданий;
- legacy EGLImage alias не получает публичного per-import cleanup; фиксированные slots либо patched importer — разные ещё не выбранные решения.

Само исследование не разрешало менять renderer/pin или запускать новые probes. По последующему явному разрешению подготовлена [целевая расширенная демка](H700_CONTRACT_PROBE.md): `contract-v2/package` прошёл build/ABI/CPU и четыре Null controls бюджета 16, не пытается завершить матрицу 17 на неподходящем backend. Затем пользователь предоставил приставку: один `capabilities` run прошёл RequestDevice, но завершился exit 1 из-за selected-layout budget mismatch; timeout не было, cleanup выполнен, firmware hashes неизменны. Нужно согласовать локальный resource/layout design, не отключать validation или автоматически менять backend. GPU workload, threading и recreation имеют отдельные границы. Ни прежний demo PASS, ни новый успешный RequestDevice не означают завершённый полный PF-03 или PF-02.

## PF-04. Выбор подхода и переход к подробному плану

По результатам составить сравнение: что подтверждено, какие изменения потребуются в каждой архитектуре, какие остаются риски и как их проверять при переносе. Успех демки — аргумент в пользу сохранения U renderer, но не автоматическое решение и не доказательство всех игровых эффектов. Подтверждённый барьер — основание оценить адаптацию старого renderer; его уже работающий вывод не надо повторять как новое исследование.

**Пользователь согласует выбор**, затем составляется подробный план реализации по правилам workflow. Полные проверки визоров, EFB copies, интерфейса, звука, управления и save/load относятся к этому плану, а не к разрастанию предплановой демки в скрытый перенос игры.
